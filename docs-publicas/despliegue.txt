DESPLIEGUE DEL BACKEND DE NÓMINA
===============================

Este documento explica cómo preparar la base de datos y cómo agregar un nuevo
objeto de negocio (BO) al endpoint único POST /api/execute.


1. ORDEN DE DESPLIEGUE DE LA BASE DE DATOS
------------------------------------------

Los archivos se aplican en este orden (todos en db/):

  1. db/migrations/001_init.sql                  tablas base
  2. db/migrations/002_esquema_seguridad.sql     esquema de seguridad
  3. db/migrations/003_zona_horaria_seguridad.sql timestamptz en seguridad
  4. db/seed-seguridad.sql                       subsistema, clases, métodos,
                                                 perfiles, permisos y opciones
  5. db/seed-login.sql                           usuario de prueba (SOLO dev)
  6. db/seed-superusuario.sql                    asigna el usuario de prueba
                                                 al perfil Superusuario (dev)

Los seeds de los pasos 5 y 6 crean el usuario admin_prueba con la clave
conocida Password123: son SOLO para desarrollo y nunca deben aplicarse en
producción.

Las migraciones se saltan si el esquema ya está aplicado, y los seeds usan
ON CONFLICT, así que se puede correr todo varias veces sobre la misma base.


2. USO DE scripts/db-setup.sh
-----------------------------

El script aplica migraciones y seeds en el orden de arriba. La conexión sale
de DATABASE_URL (no lleva credenciales).

  # Migraciones + seed-seguridad (sin usuario de prueba):
  DATABASE_URL=postgresql://usuario:clave@host:5432/base ./scripts/db-setup.sh

  # Además el usuario de prueba admin_prueba/Password123 (solo desarrollo):
  DATABASE_URL=postgresql://usuario:clave@host:5432/base ./scripts/db-setup.sh --with-test-user

Comportamiento:

  - Aborta si NODE_ENV=production (nunca toca producción).
  - Sin --with-test-user omite seed-login.sql y seed-superusuario.sql.
  - Detecta cada migración por separado: si existe `perfil` salta 001; si
    existe `subsistema` salta 002; si Bloqueado_hasta ya es timestamptz salta
    003. Imprime qué archivos aplicó y cuáles saltó.

También existe `scripts/hash-password.js` para regenerar el hash bcrypt de una
clave:

  node scripts/hash-password.js "NuevaClave123"


3. VARIABLES DE ENTORNO
-----------------------

  PORT              puerto HTTP (3000 por defecto).
  FRONTEND_URL      origen permitido por CORS.
  DATABASE_URL      cadena de conexión (obligatoria).
  DATABASE_SSL      true en Neon; false en PostgreSQL local sin SSL.
                    "no-verify" desactiva la validación del certificado y
                    solo es un escape de último recurso.
  SESSION_SECRET    obligatoria en producción; firma la cookie de sesión.
  TRUST_PROXY       saltos de proxy de confianza (1 detrás de Render,
                    Railway o nginx). Sin esto, en producción no se emite la
                    cookie secure.
  LOGIN_MAX_ATTEMPTS / LOGIN_BLOCK_MINUTES / LOGIN_FAIL_DELAY_MS
                    parámetros del bloqueo por intentos fallidos.

Si el front está en otro dominio, la cookie SameSite=Lax no viaja en las
peticiones cruzadas: hay que usar SameSite=None, Secure y trust proxy, además
de CORS con credenciales. Si el front se sirve desde el mismo dominio, Lax es
la opción correcta y CORS no hace falta.


4. CÓMO AGREGAR UN OBJETO DE NEGOCIO NUEVO
------------------------------------------

El endpoint POST /api/execute despacha por reflexión a los BO descubiertos en
src/bo/. No hay que registrar nada en el código: alcanza con seguir estos pasos.

  a) Crear el archivo src/bo/<Subsistema>/<Clase>.js y exportar la clase con el
     MISMO nombre que el archivo (nombres alfanuméricos, sin guiones):

       // src/bo/Demo/Saludo.js
       export class Saludo {
         // Recibe (db, req); la sesión se lee de req.session.
         constructor(db, req) { this.db = db; this.req = req; }

         // Solo los métodos propios del prototipo son despachables.
         hola(nombre) { return "hola " + nombre; }
       }

     El descubrimiento lee src/bo/ al arrancar y en cada Admin.reloadPermissions,
     así que un archivo nuevo se ve sin reiniciar el servidor.

  b) Sembrar en la base el subsistema, la clase, el método y el permiso. El
     subsistema debe llamarse igual que la carpeta y la clase igual que el
     archivo. Se puede seguir el patrón de db/seed-seguridad.sql:

       INSERT INTO subsistema (nombre, descripcion)
       VALUES ('Demo', 'Subsistema de ejemplo')
       ON CONFLICT (nombre) DO NOTHING;

       INSERT INTO clase (subsistema_id, nombre, descripcion)
       SELECT s.id, 'Saludo', 'Objeto de negocio de ejemplo'
       FROM subsistema s WHERE s.nombre = 'Demo'
       ON CONFLICT (subsistema_id, nombre) DO NOTHING;

       INSERT INTO metodo (clase_id, nombre, descripcion)
       SELECT c.id, 'hola', 'Devuelve un saludo'
       FROM clase c
       WHERE c.nombre = 'Saludo'
         AND c.subsistema_id = (SELECT id FROM subsistema WHERE nombre = 'Demo')
       ON CONFLICT (clase_id, nombre) DO NOTHING;

       -- Permiso del método para un perfil (p. ej. 'Superusuario').
       INSERT INTO permiso_metodo (perfil_id, metodo_id)
       SELECT pf.id, m.id
       FROM perfil pf
       JOIN clase c ON c.nombre = 'Saludo'
       JOIN metodo m ON m.clase_id = c.id AND m.nombre = 'hola'
       WHERE pf.nombre_perfil = 'Superusuario'
       ON CONFLICT DO NOTHING;

  c) Aplicar los cambios de permisos sin reiniciar. Hay dos formas:

       - Llamar por el endpoint: POST /api/execute con
         { "subsystem": "Security", "class": "Admin",
           "method": "reloadPermissions", "params": [] }
         (requiere sesión con permiso de Superusuario).

       - Reiniciar el servidor: al arrancar se cargan permisos y se
         redescubre src/bo/.

  d) Invocar el BO:

       POST /api/execute
       { "subsystem": "Demo", "class": "Saludo", "method": "hola",
         "params": ["Ana"] }

     Respuestas: 200 con el resultado; 400 si la forma es inválida; 401 sin
     sesión y sin permiso público; 403 con sesión pero sin permiso; 501 si la
     clase o el método no existen; 500 si el BO tiene un error propio (por
     ejemplo, un import roto).


5. LIMITACIONES CONOCIDAS
-------------------------

  - Sesiones en memoria: se pierden al reiniciar el proceso y no se comparten
    entre instancias. Para producción conviene un store en PostgreSQL
    (connect-pg-simple). Mientras tanto, el despliegue debe ser una sola
    instancia y asumir que un reinicio cierra las sesiones.

  - En cada petición autenticada se consulta el estado del usuario y sus
    perfiles actuales. Así una cuenta desactivada o sin perfiles deja de
    autorizar en la siguiente petición, sin esperar a que expire la cookie.
    Es una consulta indexada por petición; las peticiones públicas no la pagan.

  - El login distingue 401 (credenciales), 403 (cuenta desactivada) y 423
    (bloqueada). El tiempo de respuesta está igualado, pero el código revela
    que el usuario existe. Es una decisión de usabilidad asumida; si se
    prefiere no revelarlo, hay que unificar los tres a 401.

  - refreshBo descubre archivos nuevos de src/bo/ sin reiniciar. Los cambios en un
    archivo existente no se reimportan porque Node cachea import() por URL;
    para eso hay que reiniciar el proceso (nodemon lo hace en desarrollo).

  - `debeCambiarClave` se devuelve en el login y en getSession, y existe el
    método User.cambiarClave. El backend no bloquea los demás métodos: el
    front debe forzar el cambio de clave cuando la bandera venga en true.

  - El usuario de prueba admin_prueba/Password123 es solo para desarrollo.
    db-setup.sh lo omite sin --with-test-user y aborta si NODE_ENV=production.
