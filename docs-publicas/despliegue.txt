DESPLIEGUE DEL BACKEND DE NOMINA
================================

Guia corta de operacion. Para entender el sistema completo (arquitectura,
flujo, leyes, definiciones y formulas) leer GUIA-SISTEMA-NOMINA.txt.


1. ORDEN DE DESPLIEGUE DE LA BASE DE DATOS
------------------------------------------

Los archivos se aplican en este orden (todos dentro de db/):

  1. db/init.sql                              esquema base, SOLO sobre base vacia
  2. db/seed-seguridad.sql                    subsistemas, clases, metodos,
                                              perfiles, permisos y opciones
  3. db/migrations/001_*.sql
  4. db/migrations/002_*.sql
  5. db/migrations/003_*.sql
  6. db/migrations/004_payroll.sql            tabla registro_horas, conceptos,
                                              aportes de ley, 8 clases, 33
                                              metodos, permisos y menu
  7. db/migrations/005_listar_personas.sql    Security/User/listarPersonas
  8. db/seed-usuario-prueba.sql               admin_prueba/Password123 (SOLO dev)

El seed de seguridad va ANTES de las migraciones porque 001-005 asignan
permisos a perfiles que crea ese seed.

Las migraciones usan BEGIN/COMMIT y son idempotentes. No se edita una
migracion ya aplicada: se crea la siguiente.


2. USO DE scripts/db-setup.sh
-----------------------------

La conexion sale siempre de DATABASE_URL (el script no lleva credenciales).

  # Migraciones + seed de seguridad (sin usuario de prueba):
  DATABASE_URL=postgresql://usuario:clave@host:5432/base ./scripts/db-setup.sh

  # Ademas el usuario de prueba admin_prueba/Password123 (solo desarrollo):
  DATABASE_URL=postgresql://usuario:clave@host:5432/base ./scripts/db-setup.sh --with-test-user

Comportamiento:
  - Aborta si NODE_ENV=production (nunca toca produccion).
  - Si la tabla usuario ya existe, salta db/init.sql (evita CREATE TABLE sobre
    esquema existente).
  - Aplica siempre db/seed-seguridad.sql (idempotente).
  - Aplica en orden todos los db/migrations/NNN_*.sql.
  - Con --with-test-user agrega db/seed-usuario-prueba.sql; sin la bandera lo
    omite.

En Windows se corre desde Git Bash o WSL. Alternativa: pegar el contenido de
cada archivo en el editor SQL de Neon, respetando el orden de la seccion 1.

Antes de correr migraciones o recrear el esquema en Neon, crear un branch: es
el respaldo y el rollback instantaneo. El borron y cuenta nueva se hace en un
branch nuevo, no encima de la base en uso.


3. VARIABLES DE ENTORNO
-----------------------

  PORT                    puerto HTTP (3000 por defecto).
  DATABASE_URL            cadena de conexion (obligatoria).
  DATABASE_SSL            true (por defecto), false (PostgreSQL local sin SSL)
                          o no-verify (escape de ultimo recurso).
  SESSION_SECRET          firma la cookie de sesion; obligatoria en produccion.
  JWT_SECRET              firma el access token; obligatoria en produccion y
                          de al menos 32 caracteres.
  ACCESS_TOKEN_TTL        duracion del access token (15m por defecto).
  REFRESH_TOKEN_TTL_DIAS  duracion del refresh token (7 dias por defecto).
  FRONTEND_URLS           origenes permitidos por CORS, separados por coma.
  LOGIN_MAX_ATTEMPTS, LOGIN_BLOCK_MINUTES, LOGIN_FAIL_DELAY_MS
                          bloqueo y retardo del login.

En produccion la cookie es secure (requiere HTTPS). Si el front esta en otro
dominio, la cookie SameSite=Lax no viaja en peticiones cruzadas: hay que usar
SameSite=None, Secure y CORS con credenciales. Si el front se sirve desde el
mismo dominio, Lax es la opcion correcta.

scripts/hash-password.js regenera el hash bcrypt de una clave:

  node scripts/hash-password.js "NuevaClave123"


4. COMO AGREGAR UN OBJETO DE NEGOCIO NUEVO
------------------------------------------

El endpoint POST /api/execute despacha por reflexion a los BO descubiertos en
src/bo/. No hay que registrar nada en el codigo: alcanza con estos pasos.

  a) Crear src/bo/<Subsistema>/<Clase>.js y exportar la clase con el MISMO
     nombre que el archivo (alfanumerico, sin guiones):

       // src/bo/Demo/Saludo.js
       export class Saludo {
         constructor(db, req) { this.db = db; this.req = req; }
         hola(nombre) { return "hola " + nombre; }
       }

     Solo los metodos propios del prototipo son despachables. El archivo se ve
     sin reiniciar (refreshBo), pero un archivo ya importado no se recarga
     hasta reiniciar el proceso.

  b) Sembrar subsistema, clase, metodo y permiso en la BD (patron de
     db/seed-seguridad.sql). El subsistema debe llamarse igual que la carpeta y
     la clase igual que el archivo. Ejemplo:

       INSERT INTO subsistema (nombre, descripcion)
       VALUES ('Demo', 'Subsistema de ejemplo')
       ON CONFLICT (nombre) DO NOTHING;

       INSERT INTO clase (subsistema_id, nombre, descripcion)
       SELECT s.id, 'Saludo', 'Objeto de negocio de ejemplo'
       FROM subsistema s WHERE s.nombre = 'Demo'
       ON CONFLICT (subsistema_id, nombre) DO NOTHING;

       INSERT INTO metodo (clase_id, nombre, descripcion)
       SELECT c.id, 'hola', 'Devuelve un saludo'
       FROM clase c
       WHERE c.nombre = 'Saludo'
         AND c.subsistema_id = (SELECT id FROM subsistema WHERE nombre = 'Demo')
       ON CONFLICT (clase_id, nombre) DO NOTHING;

       INSERT INTO permiso_metodo (perfil_id, metodo_id)
       SELECT pf.id, m.id
       FROM perfil pf
       JOIN clase c ON c.nombre = 'Saludo'
       JOIN metodo m ON m.clase_id = c.id AND m.nombre = 'hola'
       WHERE pf.nombre_perfil = 'Superusuario'
       ON CONFLICT DO NOTHING;

  c) Recargar permisos sin reiniciar (requiere Superusuario):

       POST /api/execute
       { "subsystem": "Security", "class": "Admin",
         "method": "reloadPermissions", "params": [] }

     O reiniciar el servidor: al arrancar carga permisos y redescubre src/bo/.

  d) Invocar el BO:

       POST /api/execute
       { "subsystem": "Demo", "class": "Saludo", "method": "hola",
         "params": ["Ana"] }

     Respuestas: 200 con el resultado; 400 si la forma es invalida; 401 sin
     sesion y sin permiso publico; 403 con sesion pero sin permiso; 501 si la
     clase o el metodo no existen; 500 si el BO tiene un error propio.


5. VERIFICACION
---------------

  pnpm test                                  # 69 pruebas, no toca la BD
  node scripts/manual/payroll_e2e.mjs --yes  # escribe en la BD (branch desechable)

El E2E crea un empleado, horas, bono, afiliaciones y prestamo, procesa y paga
un periodo semanal, verifica los montos (575.00 / 86.63 / 488.37), comprueba
que el empleado ve su recibo y que no puede procesar periodos, y limpia sus
datos. Debe terminar con "PAYROLL E2E OK".


6. LIMITACIONES CONOCIDAS
-------------------------

  - Sesiones en memoria: se pierden al reiniciar el proceso y no se comparten
    entre instancias. Para produccion conviene un store en PostgreSQL
    (connect-pg-simple). Mientras tanto, desplegar una sola instancia.

  - En cada peticion autenticada se consulta el estado actual del usuario y sus
    perfiles. Una cuenta desactivada o sin perfiles deja de autorizar en la
    siguiente peticion, sin esperar a que expire la cookie.

  - El login distingue 401 (credenciales), 403 (cuenta desactivada) y 423
    (bloqueada). El tiempo de respuesta esta igualado, pero el codigo revela
    que el usuario existe. Es una decision de usabilidad asumida; si se
    prefiere no revelarlo, hay que unificar los tres a 401.

  - debeCambiarClave bloquea en el backend todos los metodos salvo logout y
    Security/User/cambiarClave. No es solo una advertencia para el front.

  - El usuario de prueba admin_prueba/Password123 es solo para desarrollo.
    db-setup.sh lo omite sin --with-test-user y aborta si NODE_ENV=production.
